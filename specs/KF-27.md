# KF-27 — Proactive gap discovery and recurring failure detection

**Priority:** P1 · **Depends on:** KF-26 · **Enables:** KF-28, 30, 36

## Goal / baseline

The factory currently waits for explicit gap reports and scans two regex claim shapes. Detect learning opportunities from execution outcomes, retrieval misses and corrections without converting every failure into a knowledge edit. Distinguish infrastructure/tool failures from knowledge issues.

## Contracts

`LearningCandidate{ID,WorkspaceID,DetectorVersion,Kind,Signature,Scope,ObservedRelease,FirstSeen,LastSeen,DistinctRunCount,SignalIDs,Severity,Score,Status,ReasonCodes}`; kinds `retrieval-miss`, `recurring-knowledge-failure`, `human-correction`, `repeated-tool-misuse`, `drift`, `procedure-opportunity`. Status `observed|eligible|linked|dismissed|expired`; create gap only for eligible knowledge hypothesis; procedure opportunities passed to KF-30. Tables `learning_candidates`, `candidate_signals`, `detector_checkpoints`, `candidate_gap_links`; uniqueness `(workspace,detector_version,signature,window_start)` and unique candidate+event, stable signature based on task_kind, failure class, knowledge URI/entity, relevant release/scope (not raw message/run ID). Link repeat signals across revisions to recurrence history but keep revision-specific evidence. Persist per-run distinct count, never count retries or multiple spans as independent runs.

Default detection: rolling 7-day window evaluated every 15 min, threshold >=3 distinct failed runs with same signature and at least one knowledge signal (retrieval empty, cited stale/wrong guidance, explicit correction or failed independent knowledge check); >=2 distinct human corrections of same scoped type; critical explicitly reported gap keeps existing immediate intake path. Tool timeout, network, auth, rate limit, environment outage and unknown failures alone never eligible. Threshold configurable per workspace, bounded max 100 candidates per scan and 20 new gaps/day, with operator review of backlog. Score deterministic `min(5, distinct_runs)*10 + severity_weight + correction_weight` (severity high=20, medium=10, low=0, correction >=1=10); severity from trusted detector policy, not agent claim. Ties signature order. Do not present score as probability. Candidate expiry after retention/window grace; no deletion of linked gap receipt.

## Implementation sequence

1. Implement pure detectors consuming sanitised normalised events and run summaries. Use stable canonical signatures, reason enums (`retrieval_empty`, `stale_ref`, `human_correction`, `tool_infra`, `outcome_unknown`), explicit correlation rules. A failure after retrieval alone is not knowledge causation; label hypothesis. Use known knowledge links and independent task checks when possible. Success signals tracked separately for KF-30. Add deterministic fixtures for ambiguity and mixed failures.
2. Create scheduler workflow `DiscoverLearningWorkflow` with workspace ID and checkpoint; activities page by received_at/id and use overlapping time window or recompute bounded aggregates to include late arrivals. Advance checkpoint in same transaction as candidate links/updates; duplicate pages idempotent. Re-evaluate candidates when distinct-run counts/authority change, expire stale candidates; preserve historical audit. Bounded retry, continue-as-new, no unbounded history.
3. When eligible, construct `domain.GapReport` with safe observed/expected summary and knowledge refs, `client_event_id=candidate:<id>`, synthetic actor `detector` under trusted worker identity; use existing gap service and canonical start path (KF-23), not direct proposal. Candidate-to-gap link atomic/outbox; recover after crash. Dismissal stores reason; later genuinely new evidence or release can create linked candidate. Avoid endless reopening on same evidence. Operator can list/inspect metadata (`GET /v1/learning-candidates` curator/reviewer, filter status/kind, pagination); dismiss via operator CLI with reason.
4. Add config `learning.discovery_enabled` false, interval/window/threshold/quota. Quota excess remains eligible/backlogged, not silently dropped. Metrics detector lag, signals classified, distinct runs, candidate outcomes, knowledge vs nonknowledge reasons. Do not expose raw run text.

## Security / failure handling

Candidate metadata untrusted; cannot publish or call sources directly. Restrict detector to same workspace, shareable knowledge refs. Repeated attacker-generated signals may create review load; enforce actor quotas, distinct-run count, budget and reviewer review. Correction text redacted; no raw personal data or tool arguments in generated gap. Unknown failure defaults to non-actionable; no claim of root cause. Missing cursor/store fails scan without advancing.

## Acceptance criteria / tests

- **27-A:** Three independent matching knowledge-related failures create exactly one eligible candidate and canonical gap; duplicate events/retries do not increase count.
- **27-B:** Three timeouts/auth errors with no knowledge signal produce no gap; mixed failure reasons remain uncertain unless knowledge signal present.
- **27-C:** Late event within window discovered; restart after candidate write before checkpoint creates no duplicate; candidate-to-gap outbox recovers.
- **27-D:** Two separate entities/task scopes/releases do not merge merely by error token; recurrence links prior verified gap without resetting it.
- **27-E:** Quota/backpressure leaves eligible backlog; dismissal/expiry audited and same signals do not reopen indefinitely.
- **27-F:** Workspace isolation and no secret leakage; agent cannot invoke detector as privileged actor; all new gaps follow existing curation path.

Add `internal/learning/discovery/*_test.go` or equivalent package, Temporal schedule/checkpoint tests and PostgreSQL RLS/idempotency tests. Run shared gates. **Done:** fixture replay reliably discovers knowledge hypotheses while abstaining on infrastructure/unknown failures.

## Non-goals

Automatic root-cause attribution, LLM-only detectors, incident management replacement or direct knowledge mutation.
