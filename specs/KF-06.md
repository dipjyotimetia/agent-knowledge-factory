# KF-06 Gaps

## Goal

Accept gap reports idempotently, group two agents who describe the same failure into one investigation, and keep an append-only event and audit trail. A secret in the report is rejected and is not stored.

## Inputs / outputs

- Input: a gap report plus the authenticated agent id. Client severity is stored as reported severity and is not a control signal.
- Output: a gap id and state. A repeat of `client_event_id` for the same agent returns the original id. A different agent with the same signature gets state `duplicate` and `canonical_id`.

## Non-goals

- Evidence fetching and proposal text (KF-07).
- Publishing knowledge. Reporting a gap does not modify the index.

## Interfaces

- `gaps.Service.Report`, `Status`, `List`, `Linked`, `Transition`, `Feedback`, `Events`
- `kfactory gaps list|show|triage|report`
- `factoryd -mcp` uses this store when a database is configured

States follow `new → triaged → investigating → proposal-ready → awaiting-review → accepted|rejected → published → verified`, plus `duplicate`, `insufficient-evidence`, `cancelled`, and `failed`. `CanTransition` rejects skips such as `new → published`.

## Failure modes

- Secret pattern: `ErrSecret`. The audit row records the rule name and `redacted: true`. The matched text is not in the row.
- Illegal transition: `ErrConflict`.
- Cross-workspace status read: not found, because of row-level security.
- Concurrent inserts of the same signature: one canonical row. The loser retries once and links as a duplicate.

## Tests

Two seeded reports produce one investigation linked to both submissions. The same client event id does not create a second row. An AWS access-key shaped string is rejected and absent from `audit_events`. A parallel pair ends as one `new` and one `duplicate`.

## Definition of done

`make test` covers the cases above. Knowledge content is unchanged by intake.
