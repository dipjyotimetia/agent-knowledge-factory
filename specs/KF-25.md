# KF-25 — Persistent rollback and publication quarantine

**Priority:** P0 · **Depends on:** KF-22–24

## Goal / defect

`index.Rollback` changes the active pointer but periodic reconciliation can immediately republish Git head. Rollback also accepts any indexed SHA, including a candidate. Implement durable, audited release control that survives restart and races.

## Contract and state

Extend workspace control with `publication_mode` (`normal`, `held`), generation bigint, hold reason/actor/time, last safe release. Add `release_quarantines(workspace_id,release_id or git_sha,reason_code,opened_at,cleared_at,actor,receipt_id)` and immutable `publication_control_events`. No direct DB pointer changes by CLI. `kfactory publication status`, `hold --reason`, `rollback --sha --reason`, `resume --expected-generation --reason`, `quarantine --sha --reason`, `clear-quarantine --sha --reason` (operator-only; explicit workspace config). All require operator identity, audit and confirmation for mutating commands (noninteractive explicit flag plus expected generation). Reviewer/agent API cannot invoke. Status returns active/head/held reason, generation and pending operation IDs, not content.

## Implementation sequence

1. `Hold`: transaction lock workspace, increment generation, set held, audit. `Rollback`: select target only from previously successful release receipts, rebuild from exact Git SHA if missing index and revalidate current trust/revocation policy; reject staged, quarantined, invalid, or unverifiable targets. Hold and move pointer atomically after candidate readiness; use expected generation, do not rewrite Git or reset default ref. Record previous/target receipts and reason. Preserve both indexes and ensure active status supersession handling is correct. If no safe release exists, set retrieval unavailable (503) rather than serve compromised knowledge.
2. Every release operation checks mode and generation at enqueue/evaluation/promotion. Held permits private validation and reconciliation observations but no promotion, including manual CLI index and push. Quarantine is persistent per commit/release; deny descendants containing invalid change until evaluated against a reviewed remediation, not simply by SHA inequality. Store failed release receipt and alert-safe reason. A new corrected Git commit may be evaluated while held; do not auto-resume.
3. Resume is separate action: operator specifies current generation; resolve current head, validate under same KF-22 gates including quarantine/remediation and current source authority, enqueue with new generation. Resume may leave previous release active while pending; if evaluation fails, remain/re-enter held atomically. Clearing quarantine requires operator reason and new validation; does not publish. Guard race with in-flight promote/hold by workspace row/CAS; stale candidate cannot overwrite rollback. Reconcile retries and restarts use DB state not process flags.
4. Track release effectiveness separately from gap terminal states: rollback/revocation marks proof inactive/invalidated for current serving release; prior verified event remains historical. Create linked recurrence gap on confirmed regression, no illegal state reset. Exclude quarantined content from public reads; if quarantine applies to active, atomically move to safe release or disable retrieval.
5. Upgrade existing workspaces into held mode with bootstrap verification; document emergency rollback, recovery, Git revert PR workflow and retention of last safe release artifacts. Add config validation and role restriction; no extra unauthenticated API.

## Security / failure handling

Operator identity from trusted local environment/config, not `--actor` arbitrary impersonation; if current config lacks authenticated operator mechanism, use explicit locally authorised administrative CLI with OS/DB boundary and audit (document trust). Do not give runtime app role permission to bypass release service. Audit reason length/secret scan, use stable codes. Never publish candidate or reintroduce revoked data to restore availability. If forge/DB unavailable, retain active safe pointer; failed rollback leaves hold in effect when requested. Use bounded retries and no automatic Git mutation.

## Acceptance criteria / tests

| ID | Test |
|---|---|
| 25-A | Rollback from B to A, push B/C and restart worker: A stays active while held; generation increments. |
| 25-B | Concurrent promotion paused at CAS, hold/rollback wins; stale promotion rejected. |
| 25-C | Staged/unknown/other-workspace/quarantined SHA rejected; previously approved safe revision only. |
| 25-D | Quarantine active content atomically fails closed or serves safe release; no historical read bypass. |
| 25-E | Resume stale generation fails; valid reviewed remediation passes full gate; failed eval stays held. |
| 25-F | Rollback/restart and audit chain verified; legacy verified state not presented as currently effective. |
| 25-G | Agent/reviewer cannot perform controls; operator commands idempotent and no Git mutation. |

Add `internal/publication/control_test.go`, CLI tests, PostgreSQL concurrent CAS tests and live restart integration. Update security and operations runbook. Run shared gates. **Done:** all pointer changes honor persisted control and no automatic rollback reversal.

## Non-goals

Git force-push, automated remediation merge, cross-workspace release sharing, or automated relaxation of quarantine.
