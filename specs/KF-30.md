# KF-30 — Successful procedure mining and skill synthesis

**Priority:** P1 · **Depends on:** KF-27–29

## Goal / baseline

The current `createSkill` can build a skill from a contract sentence. A knowledge factory should also learn reusable procedures from successful executions, not just correct failures. Build a deterministic success-pattern detector and bounded skill synthesis through the curator; no executable code generation/run by factory.

## Contract

`ProcedureObservation{RunID,TaskKind,AgentVersion,ReleaseID,Steps[]ActionShape,OutcomeProofID,Scope,Duration,ObservedAt}`; action shape contains allowed tool name, purpose/parameter schema IDs, ordered dependency and result category, never raw arguments/results. `ProcedureCandidate{Signature,TaskKind,Scope,DistinctSuccessRuns,DistinctActors,FailureCounterexamples,SourceEvidenceIDs,ExistingSkillRefs,Status}`. Persist `procedure_candidates`, run links, synthesis receipts. Eligible default: >=3 distinct successful runs within 14 days, independent objective task proof (test result/validator) for each, same task/scope, stable ordered action pattern, no unresolved critical counterexample; independent actors optional signal, not required. A model's self-reported success is insufficient. Config threshold/min window and quota (default 5 candidates/day), deterministic stable signature with normalized tool aliases and canonical order. Record support count and uncertainty; do not claim causality.

Skill output follows existing Agent Skills loader and `SKILL.md` format. Stable slug derived from task + scope; mandatory description/use conditions, prerequisites/access, numbered steps, expected outputs/checks, failure/abort conditions, safety constraints, source links, owner/review date; no secrets/customer values, no embedded scripts/binaries. Parameterized placeholders e.g. `<event-id>` not real data. If existing skill overlaps, propose minimal update rather than duplicate. Version via Git. `create-skill` is existing decision; update existing skill uses `update`. Each normative step linked to authoritative contract/policy or explicit reviewer-owned documented source; run evidence is supporting only. Validation uses KF-28 and candidate gate; KF-35 later tests execution.

## Implementation sequence

1. Build reducer from KF-26 events: select completed runs with independent task proof; normalise allowed tool aliases/action sequence and remove timing/arguments. Exclude retries that did not contribute, privileged/disallowed tools, cancelled/unknown runs. Treat differing order/branch as distinct unless explicit dependency graph proves equivalence; no inference from arbitrary textual commands. Group by task/entity/scope/version; count counterexamples and show competing procedures. Use same checkpoint/idempotency mechanism as KF-27.
2. On eligibility, search approved skills for task/action overlap with deterministic title/tag/step matching, record candidate references. Submit a `missing-procedure` gap or candidate link with support evidence IDs and known counterexamples. Existing active candidate reuses attempt; no repeat PR per run. Curator uses bounded KF-28 investigation to inspect contracts, existing skills, successful observations and failure contexts. If no authoritative support for action, abstain or ask reviewer to document it; no claims merely because runs succeeded.
3. Synthesis creates one minimal candidate skill or patch; validate path containment, frontmatter, required sections, skill naming, references and permissions. Never execute skill scripts; new script/binary generation disallowed. Check duplicate slugs and near-identical procedure. Before PR, evaluate retrieval discoverability and negative cases (not suggested for unrelated tasks); no execution claims until KF-35. Review instructions show support count, source citations, counterexamples and scope; no raw trace data.
4. Add config `learning.procedure_mining_enabled=false`, window/threshold/quota; operator listing via learning candidate surface. Store accepted/rejected/merged link and post-publication effectiveness placeholder; recurrence if new failure evidence. Update banking fixtures with synthetic run patterns for test-data preparation or event verification, no external repo edits.

## Security / failures

Successful execution is not permission to repeat a privileged action. Reject procedure containing bypassed auth, destructive changes, data export or raw payload. Scope inheritance from sources; only shareable guidance. Treat model-produced skill text as untrusted; never execute or grant permissions. If pattern includes unknown tool, inconsistent task proof, unresolved safety issue or invalid source, no proposal. Quota failure leaves backlog; duplicate signals cannot inflate support.

## Acceptance criteria / tests
- **30-A:** Three independent verified successful runs create one candidate and skill proposal; duplicates/retries count once.
- **30-B:** Self-reported success, unknown outcome, disallowed tool or failed objective check not eligible; conflicting success/failure pattern escalates.
- **30-C:** Existing matching skill updated instead of duplicate; unrelated task does not retrieve candidate skill.
- **30-D:** Generated skill passes existing loader, includes required prerequisites/checks/scope/evidence, contains no script or real payload; unsupported step rejected.
- **30-E:** Candidate remains private until human merge and KF-22 gate; reviewer rejection produces no published skill.
- **30-F:** Repeated schedule/restart produces one logical candidate and PR, actor/workspace isolation and no raw trace in Git.

Add `internal/learning/procedure` tests, curator/skills loader tests, synthetic banking fixture and workflow integration. Run shared gates. **Done:** repeatable successful experience can lead to a reviewable reusable skill, without auto-learning unsafe procedures.

## Non-goals

Automatic script execution, tool permission expansion, model training, general process-mining platform or proof of task-level improvement before replay.
