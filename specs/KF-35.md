# KF-35 — Agent execution replay and comparative evaluation

**Priority:** P2 · **Depends on:** KF-25, KF-26, KF-34 · **Enables:** KF-36, KF-38

## Goal / baseline

`evaluations.RunRetrieval` passes when an answer occurs in any top-k document; `RunDecisions` tests fixed curator inputs and is not an agent execution benchmark. Demonstrate whether a knowledge revision changes actual task outcomes, and use the same evaluation gate for release candidates. Separate deterministic test results from live model-dependent evidence. Do not execute untrusted source/skill scripts.

## Contract / schemas

Add versioned `TaskCaseV1` (JSON schema `schemas/task-case.schema.json`) with `case_id`, `dataset_version`, `task_kind`, `task_prompt`, `fixture_id`, `initial_state_digest`, `allowed_tools`, `max_steps`, `timeout_ms`, `max_tokens`, `critical`, `success_checks[]` (typed evaluator ID + parameters), `negative_checks[]`, `expected_knowledge_refs`, `target_gap_ids` or explicit mapping in proposal metadata, `split: development|held-out`, and `risk_class`. Golden checks/answers are evaluator-only; agent receives task prompt, permitted tool descriptions and retrieved knowledge, never golden outputs, hidden cases, or candidate labels. Split fixtures by task family/entity where feasible, avoid leakage; dataset immutable digest includes case definitions and fixture version.

`ReplayRequest{EvaluationID,DatasetDigest,BaselineReleaseID,CandidateID or ReleaseID,AgentConfigDigest,ToolConfigDigest,ModelID,SeedPolicy,Repetitions}`. `ReplayResult{case_id,arm,trial,release_or_candidate_id,task_outcome: pass|fail|invalid,check_results,knowledge_citations,tool_count,latency_ms,input_tokens,output_tokens,cost_optional,reason_codes,artifact_digest}`. `EvaluationReceipt` binds comparison to exact baseline/candidate, policy, dataset, runner and config digest. Tables `execution_datasets`, `execution_cases`, `execution_comparisons`, `execution_trials`, `trial_checks`, `gap_evaluation_links`; append-only, unique comparison+case+arm+trial. Add `kfactory eval replay --baseline <release> --candidate <candidate-id|release> --dataset <path> --runner fixture|model --repetitions N`, trusted operator/worker only; metadata-only evaluation read endpoint, no public historical knowledge access.

## Implementation sequence

1. Build `internal/evaluations/replay` with `Runner.Run(ctx, TaskCase, RunEnvironment, KnowledgeReader) (Outcome,error)` and `Checker.Check(ctx, immutableFixtureState, outcome)`. Runner gets scoped read-only evaluation capability from KF-24/34, pinned release/candidate, not public MCP get with arbitrary SHA. Checks are allowlisted compiled Go functions: schema/field correctness, expected tool invocation pattern, synthetic state assertions, generated patch structure and fixture tests, prohibited action. No model-as-judge as sole critical gate. Separate check config from prompt; validate case/dataset before execution. Fixture runner deterministic and substantive: task policy selects action based on actual retrieved knowledge, exercises typed tool and validates state, not returns hardcoded answer by arm.
2. Isolate executions: independent fixture clone/reset per arm/trial; no customer data, live service credentials, unrestricted network, arbitrary shell or skill scripts. Default use in-process fake tools and allowlisted Go assertions. If generated code tests required, optional explicitly enabled sandbox (nonroot, read-only base, isolated writable temp, resource/time cap, no network/host mounts/credentials), run only fixed evaluator command, never source instructions. No sandbox dependency in default CI. Invalid environment = invalid trial, never success. Candidate content untrusted; runner cannot publish or write evidence repos. Never share model conversation/cache between arms.
3. Paired evaluation: use identical case prompt, model/version, agent/tool config, tool fixtures, timeout and token budget. For deterministic runner 1 repetition sufficient; for live stochastic provider default 3 paired repetitions, configurable bounded <=10, balanced order deterministic by case/trial seed; if seed not supported record it. Store per-trial outcome and retrieval refs. Aggregate pass rate over eligible paired trials, paired difference, counts of improved/regressed/tied, invalid trials and reasons, latency/token distribution. Report confidence interval only with appropriate sample size/method (paired bootstrap by case, seeded, disclose small-sample limitations); no fabricated significance or causality. Cost only if documented tariff and usage captured. Live model results opt-in, never claimed if not run.
4. Gate integration: before PR and publication, evaluate same immutable dataset and config against actual candidate with KF-22; critical previously passing paired case must not regress in deterministic CI; any forbidden action/critical safety failure blocks regardless of prior baseline. Required trial invalid/timeout -> gate unavailable/fail closed, not ignored. For stochastic production gates require explicitly configured repetition/pass threshold and no critical safety failure; record uncertainty. Noncritical improvement optional for publication, but gap verified only when explicitly linked targeted case failed baseline and passes candidate at defined threshold, actual merge effect present. Replace answer-substring `TargetedIDs` mapping with explicit stable case links, do not use model golden answers to choose fixes. Store actual revisions and receipt; generation fence on promote. Preserve retrieval/unit decision gates as separate phases.
5. Ship >=15 synthetic execution cases across contract evolution, procedure discovery, data access, retry/compensation and security/negative cases, including >=5 critical cases and held-out cases not used to synthesise skill. At least one fixture task actually fails on stale knowledge and passes after reviewed edit. Baseline fixture includes no-knowledge control arm optionally (separate benchmark, not publication gate). Produce JSON/Markdown machine-readable report and exact run command. Live provider tests opt-in, no required API key for CI.

## Security / failure handling

Evaluator credentials and gold data never available to curator/agent. Internal candidate/historical reads scoped to eval operation and permission policy; revoked data blocked even for replay unless sanitised synthetic fixture. Do not execute arbitrary generated scripts or source code with host credentials. Limit attempts, tokens and execution time; cancel/reset fixtures. Audit only safe IDs/check results. Store no raw prompts from real runs; fixture prompts safe. Missing checks, dataset/version drift, invalid paired trial or tampered receipt prevents promotion. Avoid selecting only favourable tasks or excluding failed trials silently.

## Acceptance criteria / tests
- **35-A:** Same runner/model/tool config with stale vs corrected release yields independently checked fail→pass; retrieval alone is insufficient for pass.
- **35-B:** Critical regression, forbidden action or invalid required trial blocks candidate promotion; active revision unchanged.
- **35-C:** Golden answers/check params unavailable to agent/curator; attempt to access private candidate outside evaluation denied.
- **35-D:** Both arms reset identical fixtures, no network/live credentials, deterministic runner repeatable; optional live report clearly identified and config recorded.
- **35-E:** Explicit gap-case link proves only matching gap, no substring-based verification; unrelated gaps not verified.
- **35-F:** Idempotent replay, cancellation/restart and concurrent candidates produce immutable independent receipts; no cross-workspace reads.
- **35-G:** Report gives paired denominators, invalid trials, safety regressions and measured latency/tokens; no invented numbers, held-out split recorded.

Add `internal/evaluations/replay/*_test.go`, schema and sandbox negative tests, publication gate integration, `examples/banking/tests/execution-cases.json`. Run shared gates and deterministic benchmark; report actual results and optional live test status. **Done:** independently measurable agent task improvement using same execution config and changed knowledge, with fail-closed critical gates.

## Non-goals

Universal agent benchmark, model training, mandatory LLM-as-judge, arbitrary code execution, unrestricted real system replay, production traffic reproduction.
